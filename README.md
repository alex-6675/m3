# ПЛАН ОТКРЫТИЯ ВЕТКИ «МОИ ЗАПИСКИ» (тезисы, v1)

## 0. Идентичность (не путать)
- «Мои записки» ≠ «Всевидящий глаз портала VK».
- Продукт = личная записная книжка встреч и наблюдений.
- VK — один из источников изъятия, не идентичность продукта.
- Маркировка на портале — только по требованию (скальпель),
  по умолчанию ВЫКЛ. Постоянного «глаза» нет.

## 1. Цели
Ц1. Вторая память: записи о персонах/сообществах (кто, где, когда,
    суть контакта), независимые от портала.
Ц2. Сохранение личных связей и наблюдений во времени
    (журнал пользователя глубиной 4 года — первичные данные).
Ц3. Архитектурная готовность к более массивной глобальной задаче
    (формулируется позднее; ветка открывается так, чтобы расти).

## 2. Задачи
З1. Открыть репо/линию; перенести общее ядро (provenance-хэш).
З2. Контейнер записей: схема карточки v3 + теги (R9, облако по
    образцу blogspot) + журнал контактов (даты, суть, ответ).
З3. Каналы изъятия: VK через общее ядро; РУЧНОЙ ввод (запись без
    портала); позже OK и иные источники.
З4. Экспорт/резерв: CSV / vCard / MPE (Google) — данные переносимы.
З5. Личный интерфейс записок (поиск по имени/тегу, лента журнала) —
    кабинет, а не наблюдательный пост.

## 3. Методы реализации
М1. Старт НЕ от первичного донора (донор не стартанул — не ждём его):
    старт от доказанно рабочего общего ядра context-vkru; от доноров
    (dmiandr/context, Trovonicknamecolorizer) — только отдельные
    механики (облако тегов, персона→свойство→маркировка).
М2. Копия ядра одним sync-коммитом с provenance-хэшем (SPLIT v5/v7);
    фиксы ядра — только у донора ядра, в ветку — sync-коммитом.
М3. Регламенты те же: AGENTS/HANDOVER-стиль, лимиты Л1–Л5, роли
    (пользователь — смыслы и вердикты; проектировщик — код;
    кодер — тексты), КК как мера.
М4. Хранилище: локальное (chrome.storage.local / файл); IndexedDB —
    только когда объём потребует (SPLIT v7).
М5. Зрение агента (Edge MCP/CDP) для диагностики; слепых циклов нет.
М6. Движений пользователя за цикл: 0 или 1 (вердикт по картинке).

## 4. Сроки годности и ревизии
- Триггер открытия: достижение mem-2026 рубежа M1 (публичный раздел
  «Захороненные» + трек А «плиты» в работе) ИЛИ +60 дней от даты
  плана — что раньше.
- Этап 1 (контейнер + переезд ядра и базы): 14 дней.
- Этап 2 (каналы изъятия + ручной ввод): 30 дней.
- Этап 3 (теги, экспорт, интерфейс): по готовности, без гонки.
- Ревизия этапа: каждые 30 дней (закрыт / продлён / заменён методом).
- Срок годности плана: 180 дней; после — пересборка от фактов.
- Л2 в силе: ≤2 итераций на дефект, затем смена метода.

## 5. Основа к переезду (что переезжает)
- Код: ядро (normalize/storage/messaging), изъятие (ПКМ), диалог
  карточки, стекло (если к триггеру готово).
- Регламенты: AGENTS/HANDOVER/SPLIT, лимиты Л1–Л5, REQUESTS.md.
- Данные: личная база (75 карточек, ctxdb) + журнал пользователя
    (4 года) как первичный источник.
- НЕ переезжает: мемориальные данные mem-2026 (павшие, потомки,
  плиты) — остаются в своей ветви; базы не смешиваются.

## 6. Этический контур (не делается в «Моих записках»)
- Массового сбора нет; только точечное изъятие и ручной ввод.
- Никакой публикации данных живых персон без решения пользователя.
- «Грязь»/блеклость — только личный инструмент, не публичный.
